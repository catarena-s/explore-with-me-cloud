# Правила проверки работы с проектом

Данный документ содержит проверочные требования для оценки качества работы с проектом. Все требования должны быть легко проверяемы вручную.

## 1. Формат ответа

### 1.1. Обязательная структура ответа

Ответ должен содержать **все четыре раздела** в указанном порядке:

#### ✅ Проверка наличия разделов

- [ ] **Раздел "План"** присутствует
- [ ] **Раздел "Изменения"** присутствует
- [ ] **Раздел "Объяснение"** присутствует
- [ ] **Раздел "Проверка"** присутствует

#### ✅ Проверка содержания раздела "План"

- [ ] Описано, что нужно сделать (краткое резюме задачи)
- [ ] Перечислены шаги выполнения (минимум 2 шага)
- [ ] Указаны файлы, которые будут затронуты (конкретные пути к файлам)
- [ ] Указаны модули/сервисы, которые будут изменены

**Пример правильного плана:**
```
### План
- Добавить новый эндпоинт для получения популярных событий
- Шаги:
  1. Добавить метод в PublicEventController
  2. Реализовать логику в EventService
  3. Использовать существующий EventShortDto
- Файлы:
  - ewm-main/ewm-event/.../PublicEventController.java
  - ewm-main/ewm-event/.../EventService.java
```

#### ✅ Проверка содержания раздела "Изменения"

- [ ] Указано, какие именно изменения были сделаны
- [ ] Указаны конкретные файлы, которые были изменены
- [ ] Указаны конкретные методы/классы, которые были добавлены/изменены
- [ ] Указано, использовались ли существующие компоненты (DTO, исключения и т.д.)

**Пример правильного описания изменений:**
```
### Изменения
- Добавлен метод getPopularEvents в PublicEventController
- Реализован метод getPopularEvents в EventServiceImpl
- Использован существующий EventShortDto (без создания нового)
- Изменённые файлы:
  - PublicEventController.java
  - EventServiceImpl.java
```

#### ✅ Проверка содержания раздела "Объяснение"

- [ ] Объяснено, что было изменено
- [ ] Объяснено, почему выбран именно этот подход
- [ ] Указаны возможные побочные эффекты (или указано, что их нет)
- [ ] Указана необходимость тестирования

**Пример правильного объяснения:**
```
### Объяснение
- Добавлен новый публичный эндпоинт для получения популярных событий
- Использован существующий DTO для обеспечения консистентности API
- Побочных эффектов нет, так как добавлен только новый эндпоинт
- Требуется тестирование: проверка сортировки, пагинации, обработки пустого списка
```

#### ✅ Проверка содержания раздела "Проверка"

- [ ] Указано, что код компилируется без ошибок
- [ ] Указано, что проверено соответствие архитектурным ограничениям
- [ ] Указано, что проверено отсутствие нарушений существующего функционала
- [ ] Указаны конкретные проверки, которые были выполнены

**Пример правильной проверки:**
```
### Проверка
- Код компилируется без ошибок
- Соответствие архитектурным ограничениям: использованы существующие DTO, не изменены общие модули
- Существующий функционал не нарушен: добавлен только новый эндпоинт
- Проверено: компиляция, соответствие структуре проекта, отсутствие изменений в общих модулях
```

### 1.2. Запрещённые форматы

#### ❌ Неправильные форматы ответа

- [ ] Ответ начинается сразу с изменений без плана
- [ ] Отсутствует раздел "Объяснение"
- [ ] Отсутствует раздел "Проверка"
- [ ] План не содержит список файлов
- [ ] Изменения описаны слишком общо без конкретики

## 2. Обязательные шаги

### 2.1. Перед началом работы

#### ✅ Проверка обязательных шагов перед изменениями

- [ ] Выполнен анализ существующего кода (использованы read_file, codebase_search)
- [ ] Определены зависимости и связанные компоненты
- [ ] Проверено соответствие архитектурным ограничениям из .cursorrules
- [ ] Определены все файлы, которые будут затронуты

### 2.2. Во время работы

#### ✅ Проверка выполнения изменений

- [ ] Изменения выполнены с использованием соответствующих инструментов (search_replace, write и т.д.)
- [ ] Не использованы запрещённые изменения (из раздела "Что НЕЛЬЗЯ изменять" в .cursorrules)
- [ ] Использованы существующие компоненты, если это возможно (DTO, исключения из ewm-utils)
- [ ] Соблюдена структура проекта и пакетов

### 2.3. После выполнения изменений

#### ✅ Проверка завершающих шагов

- [ ] Выполнена проверка компиляции (явно указано в разделе "Проверка")
- [ ] Проверено соответствие архитектурным ограничениям
- [ ] Проверено отсутствие нарушений существующего функционала
- [ ] Предоставлен список всех изменённых файлов

## 3. Правила остановки перед коммитом

### 3.1. Обязательные действия перед коммитом

#### ✅ Проверка обязательных действий

- [ ] **ОСТАНОВКА** — коммит НЕ выполнен автоматически
- [ ] Предоставлен **список изменённых файлов** (конкретные пути)
- [ ] Предложено **сообщение коммита** в правильном формате
- [ ] Выведен текст **"Изменения готовы к коммиту"**
- [ ] Ожидается явное подтверждение пользователя

### 3.2. Формат списка изменённых файлов

#### ✅ Проверка формата списка файлов

- [ ] Список начинается с заголовка "## Изменённые файлы" или "**Изменённые файлы:**"
- [ ] Каждый файл указан с полным путём относительно корня проекта
- [ ] Указано, является ли файл новым или изменённым
- [ ] Список упорядочен (например, по алфавиту или по логике изменений)

**Пример правильного списка:**
```
## Изменённые файлы

- `ewm-main/ewm-event/src/main/java/.../PublicEventController.java` (изменён)
- `ewm-main/ewm-event/src/main/java/.../EventServiceImpl.java` (изменён)
```

### 3.3. Формат сообщения коммита

#### ✅ Проверка формата сообщения коммита

- [ ] Использован правильный префикс: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`
- [ ] Первая строка содержит краткое описание (до 50 символов)
- [ ] Дополнительные строки содержат детальное описание изменений
- [ ] Указаны затронутые модули/сервисы
- [ ] Сообщение понятно и информативно

**Примеры правильных сообщений:**

```
feat: добавить эндпоинт для получения популярных событий

Добавлен GET /events/popular в PublicEventController.
Реализована логика сортировки по количеству подтверждённых заявок.
Использован существующий EventShortDto.

Модуль: ewm-event
```

```
fix: исправить валидацию даты события

Добавлена проверка, что дата события не может быть в прошлом
и должна быть минимум через 2 часа от текущего момента.
Используется ValidateException из ewm-utils.

Модуль: ewm-event
```

### 3.4. Запрещённые действия

#### ❌ Неправильные действия перед коммитом

- [ ] Коммит выполнен автоматически без остановки
- [ ] Не предоставлен список изменённых файлов
- [ ] Не предложено сообщение коммита
- [ ] Не выведен текст "Изменения готовы к коммиту"
- [ ] Выполнен `git add` без явного запроса пользователя
- [ ] Выполнен `git commit` без явного подтверждения пользователя

### 3.5. Проверка текста "Изменения готовы к коммиту"

#### ✅ Проверка наличия текста

- [ ] Текст **"Изменения готовы к коммиту"** присутствует в ответе
- [ ] Текст выведен после списка файлов и сообщения коммита
- [ ] После текста следует остановка (нет автоматического выполнения коммита)

## 4. Дополнительные проверки

### 4.1. Соответствие архитектурным ограничениям

#### ✅ Проверка соблюдения ограничений

- [ ] Не изменены общие модули (ewm-dto, ewm-utils) без согласования
- [ ] Не изменена структура аутентификации
- [ ] Не изменены имена сервисов и порты
- [ ] Не изменены структуры RabbitMQ сообщений
- [ ] Не изменены имена таблиц в БД
- [ ] Все изменения БД выполнены через Liquibase (если применимо)

### 4.2. Качество кода

#### ✅ Проверка качества

- [ ] Использованы существующие DTO и исключения, если возможно
- [ ] Код следует структуре проекта
- [ ] Не созданы дублирующиеся компоненты
- [ ] Изменения логичны и понятны

## 6. Примеры неправильных ответов

### ❌ Пример 1: Отсутствует план

```
Я добавил новый эндпоинт в контроллер.
[Изменения выполнены]
```

**Проблемы:**
- Нет раздела "План"
- Нет раздела "Объяснение"
- Нет раздела "Проверка"
- Нет списка изменённых файлов

### ❌ Пример 2: Автоматический коммит

```
[Изменения выполнены]
[git commit выполнен автоматически]
```

**Проблемы:**
- Нет остановки перед коммитом
- Нет списка файлов
- Нет предложенного сообщения коммита
- Нет текста "Изменения готовы к коммиту"

### ❌ Пример 3: Неполный план

```
План: добавить эндпоинт
[Изменения выполнены]
```

**Проблемы:**
- План не содержит список файлов
- План не содержит шаги выполнения
- Нет раздела "Объяснение"
- Нет раздела "Проверка"

### Изменения

### Объяснение
