# Примеры сценариев работы с проектом

Данный документ содержит примеры типичных задач и ожидаемый формат работы с ними.

## Сценарий 1: Добавление функциональности

### Пример промпта

```
Добавь эндпоинт GET /events/popular для получения списка популярных событий.
Эндпоинт должен:
- возвращать события, отсортированные по количеству подтверждённых заявок
- поддерживать пагинацию (from, size)
- быть публичным (не требует аутентификации)
- использовать существующие DTO
```

### Ожидаемый формат ответа

#### 1. План
- Анализ существующей структуры контроллеров и сервисов
- Определение необходимых изменений:
  - Добавление метода в `PublicEventController`
  - Добавление метода в `EventService` и `EventServiceImpl`
  - Использование существующих DTO (`EventShortDto`)
- Файлы для изменения:
  - `ewm-main/ewm-event/src/main/java/dev/shvetsova/ewmc/event/api/PublicEventController.java`
  - `ewm-main/ewm-event/src/main/java/dev/shvetsova/ewmc/event/service/event/EventService.java`
  - `ewm-main/ewm-event/src/main/java/dev/shvetsova/ewmc/event/service/event/EventServiceImpl.java`
  - `ewm-main/ewm-event/src/main/java/dev/shvetsova/ewmc/event/repo/EventRepository.java` (если нужен новый метод)

#### 2. Изменения
- Реализация метода в контроллере
- Реализация бизнес-логики в сервисе
- Добавление метода в репозиторий (если требуется)
- Использование существующих DTO без изменений

#### 3. Объяснение
- Описание добавленного функционала
- Объяснение выбора подхода (почему использованы существующие DTO, почему публичный эндпоинт)
- Указание на необходимость тестирования

#### 4. Проверка
- Проверка компиляции
- Проверка соответствия архитектурным ограничениям
- Убедиться, что не нарушена существующая функциональность

### Критерии готовности

- [ ] Эндпоинт добавлен в `PublicEventController`
- [ ] Метод в сервисе реализован и использует правильную сортировку
- [ ] Пагинация работает корректно
- [ ] Используются существующие DTO (без создания новых)
- [ ] Код компилируется без ошибок
- [ ] Соответствует архитектурным ограничениям (не изменены общие модули, не нарушена структура)
- [ ] Предложено сообщение коммита в формате `feat: добавить эндпоинт для получения популярных событий`

## Сценарий 2: Исправление бага

### Пример промпта

```
Исправь баг: при создании события с датой в прошлом не выбрасывается исключение.
Событие должно создаваться только с датой в будущем (минимум через 2 часа от текущего момента).
```

### Ожидаемый формат ответа

#### 1. План
- Поиск места валидации даты события
- Анализ текущей логики создания события
- Определение необходимых изменений:
  - Добавление/исправление валидации даты в сервисе
  - Возможно, добавление валидации в DTO
- Файлы для изменения:
  - `ewm-main/ewm-event/src/main/java/dev/shvetsova/ewmc/event/service/event/EventServiceImpl.java`
  - Возможно: `ewm-dto/src/main/java/dev/shvetsova/ewmc/dto/event/NewEventDto.java`

#### 2. Изменения
- Добавление проверки даты события
- Выброс исключения `ValidateException` при нарушении правила
- Использование существующих исключений из `ewm-utils`

#### 3. Объяснение
- Описание найденной проблемы
- Объяснение решения (почему выбрано именно это исключение, почему именно 2 часа)
- Указание на необходимость тестирования с различными датами

#### 4. Проверка
- Проверка компиляции
- Проверка, что валидация работает корректно
- Убедиться, что не сломана существующая функциональность

### Критерии готовности

- [ ] Валидация даты добавлена/исправлена
- [ ] Исключение выбрасывается при дате в прошлом или менее чем через 2 часа
- [ ] Используется существующее исключение из `ewm-utils` (не создано новое)
- [ ] Код компилируется без ошибок
- [ ] Не нарушена существующая функциональность
- [ ] Предложено сообщение коммита в формате `fix: исправить валидацию даты события`

## Сценарий 3: Рефакторинг без изменения поведения

### Пример промпта

```
Вынеси общую логику проверки прав доступа к событию в отдельный метод.
Метод должен проверять, является ли пользователь инициатором события.
Используй этот метод во всех местах, где выполняется такая проверка.
```

### Ожидаемый формат ответа

#### 1. План
- Поиск всех мест, где выполняется проверка прав доступа к событию
- Анализ текущей логики проверки
- Определение сигнатуры нового метода
- Определение необходимых изменений:
  - Создание приватного метода в сервисе
  - Замена дублирующегося кода на вызов нового метода
- Файлы для изменения:
  - `ewm-main/ewm-event/src/main/java/dev/shvetsova/ewmc/event/service/event/EventServiceImpl.java`

#### 2. Изменения
- Создание приватного метода `checkEventInitiator` или аналогичного
- Замена всех дублирующихся проверок на вызов нового метода
- Сохранение существующего поведения (те же исключения, те же сообщения)

#### 3. Объяснение
- Описание найденных дублирований
- Объяснение выбора места для нового метода
- Указание на то, что поведение не изменилось

#### 4. Проверка
- Проверка компиляции
- Проверка, что все проверки заменены
- Убедиться, что поведение не изменилось (те же исключения, те же условия)

### Критерии готовности

- [ ] Общий метод создан
- [ ] Все дублирующиеся проверки заменены на вызов нового метода
- [ ] Поведение не изменилось (те же исключения, те же условия)
- [ ] Код компилируется без ошибок
- [ ] Код стал более читаемым и поддерживаемым
- [ ] Предложено сообщение коммита в формате `refactor: вынести проверку прав доступа к событию в отдельный метод`

## Общие критерии для всех сценариев

### Перед коммитом

- [ ] Все изменения выполнены
- [ ] Код компилируется без ошибок
- [ ] Соответствие архитектурным ограничениям проверено
- [ ] Список изменённых файлов предоставлен
- [ ] Сообщение коммита предложено
- [ ] Текст "Изменения готовы к коммиту" выведен
- [ ] Ожидается явное подтверждение пользователя перед коммитом

### Формат сообщения коммита

- Используется префикс: `feat:` для новой функциональности, `fix:` для исправлений, `refactor:` для рефакторинга
- Первая строка — краткое описание (до 50 символов)
- Дополнительные строки — детальное описание изменений
- Указаны затронутые модули/сервисы

### Архитектурные ограничения

- Не изменяются общие модули (`ewm-dto`, `ewm-utils`) без согласования
- Не нарушается структура аутентификации
- Не изменяются имена сервисов и порты
- Не изменяются структуры RabbitMQ сообщений
- Не изменяются имена таблиц в БД
- Все изменения БД через Liquibase
- Используются существующие DTO и исключения, если возможно
